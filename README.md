# Roommate Chore Manager

CS250 Group 10

Roommate Chore Manager is a web app that helps people who share a home keep track of who is responsible for which chore, when it's due, and whether it's done.

This is an early prototype. Right now you can create a household and look one up by its code. The chore features are still planned.

## What works and what doesn't

**Working**

- Creating a household from a form in the browser. The server checks the name, generates a household code, saves it to Supabase, and sends the record back to the page.
- Looking up a household by its code (`POST /api/join-household`).
- One automated test for household creation, run by GitHub Actions on pull requests.

**Not built yet**

- Household membership and access control. Creating a household doesn't add the creator as a member.
- A join screen. The lookup endpoint exists, but it doesn't add a member or open a dashboard.
- Creating and assigning chores, marking them complete, and completion history
- Weekly schedule, recurring rotation, and overdue views

The diagrams in `docs/uml/` show the planned design (User, Household, Chore, ChoreAssignment, CompletionRecord). The running code doesn't use those classes yet. Requests are handled directly in `backend/server.js`, and `src/Household.js` is an unused stub.

## How it fits together

```
Browser form  ->  Express (backend/server.js)  ->  Supabase "Household" table
```

- **Frontend:** plain HTML and JavaScript in `frontend/`, no build step.
- **Backend:** Express on Node.js in `backend/`. It also serves the frontend, so there's only one thing to start.
- **Database:** Supabase. The key stays on the server and is never sent to the browser.

## Running it locally

### You'll need

- Git
- Node.js 22 (the GitHub workflow uses 22 too)
- Access to a Supabase project, its URL, and its server-side secret key. Ask the current database owner for access and get the key from them privately. Never commit it or put it in the frontend.

### Steps

1. Clone the repo and go into the backend folder:

   ```sh
   git clone https://github.com/Garcia-X/CS250-Group.git
   cd CS250-Group/backend
   ```

2. Install the dependencies. `npm ci` installs the exact versions in `package-lock.json`:

   ```sh
   npm ci
   ```

3. Create a file named `.env` in `backend/`:

   ```dotenv
   SUPABASE_URL=https://YOUR_PROJECT.supabase.co
   SUPABASE_SECRET_KEY=YOUR_SERVER_SIDE_KEY
   ```

   `backend/.gitignore` already excludes `.env`. Start the server from `backend/` so it can find the file.

4. Set up the database (see the next section).

5. Start the server:

   ```sh
   node server.js
   ```

   You should see `Server running on http://localhost:3000`. There's no `npm start` script.

6. Open http://localhost:3000 in your browser. Don't open `frontend/index.html` as a file, because the form needs the server.

7. Enter a household name and submit. You should see "Household Created Successfully" with the name, household ID, and unique ID. Check that the row shows up in the Supabase `Household` table.

Stop the server with Ctrl+C.

## Database setup

Cloning the repo doesn't give you the database, and the original schema and credentials aren't in it.

**Using the team's existing database:** get project access and a schema export from the current owner. The code expects a case-sensitive table named `Household` with these columns:

| Column | Used for |
|--------|----------|
| `household_id` | Generated by the database and returned after creation |
| `name` | The household name |
| `unique_id` | The household code generated by the server |

The server inserts `name` and `unique_id`, so the database has to generate `household_id` on its own. We worked these columns out from `server.js` and the test. Column types, defaults, and policies still need to be confirmed against the real database.

**Starting a fresh Supabase project:** `docs/setup/household-bootstrap.sql` is a proposed minimal schema that matches the code. Run it in the new project's SQL editor. It isn't an export of our database, so don't run it against an existing table.

## API

| Route | Body | Success | Other responses |
| --- | --- | --- | --- |
| `POST /api/household` | `{"name":"Room 10"}` | 201 and the new household | 400 for a missing, non-string, or blank name; 500 if saving fails |
| `POST /api/join-household` | `{"uniqueId":"CODE"}` | 200 and the matching household | 404 if no match, or if the database returns any error |

Names are trimmed before they're saved. The join endpoint only looks up a record. It doesn't check a login, add a member, or open a dashboard, and neither endpoint checks permissions.

To try the lookup, POST the JSON above to `http://localhost:3000/api/join-household` with `Content-Type: application/json`.

## Testing

From `backend/`:

```sh
npm test -- --runInBand
```

The test in `backend/automated.test.js` sends a creation request and checks for a 201, the submitted name, a `unique_id`, and a `household_id`. It starts the app itself, so you don't need the server running, but it does need a working `.env`.

A few things to know:

- It uses the real database and leaves a row named `Automated Test For Household` behind every time. Use a test database and delete only your own test rows.
- It's the only test. Invalid input, failed lookups, and permissions aren't covered.

`.github/workflows/household-creation-api-test.yml` runs `npm test` on pull requests and manual runs, not on every push. It needs repository secrets named `SUPABASE_URL` and `SUPABASE_SECRET_KEY`. Whether a failure blocks merging depends on the repo's branch rules.

## Troubleshooting

| Problem | What to check |
| --- | --- |
| `npm start` fails | There's no start script. Use `node server.js` from `backend/`. |
| Supabase URL or key error at startup | Make sure `.env` is in `backend/` and both variables are set. |
| "Failed to create household" | Look at the request status, then the database access, table name, and columns. |
| `EADDRINUSE` | Something else is using port 3000. Stop it and restart. |
| Jest fails or times out | Check your connection, credentials, schema, and database permissions. |

## Known issues

- No membership or access rules. Keeping the key on the server doesn't control who can see which household.
- The join route reports any database error as "Household not found," and it fails instead of returning a clean error if the request has no body.
- The frontend puts the household name into the page as raw HTML. Switch to safe text rendering before letting untrusted users near it.
- The frontend doesn't handle network errors or double submits, and only shows a generic message when creation fails.
- Household codes come from `Math.random()` and aren't checked for duplicates. Confirm the database enforces uniqueness and add a retry.
- `src/Household.js` is unused.
